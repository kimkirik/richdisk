# 드럼스코어 개발 인수인계

정리 기준일은 2026-10-05입니다. 다른 채팅에서 이 문서와 README를 먼저 읽고 개발을 이어가세요. 현재 버전은 개인 맥에서 음악을 드럼 스템으로 분리하고 채보하는 앱입니다. 창 전환 후 복구 기능은 구현됐지만, 정답 악보와 대조한 채보 정확도 평가는 아직 끝나지 않았습니다.

## 사용자 요구와 변경 범위

- MP3 등 음악을 넣으면 드럼을 분리하고 악보로 만들고 싶습니다. 정확도를 중요하게 생각하며 전문가 수준의 결과를 원하지만, 현재 모델이 이를 보장하는 상태는 아닙니다.
- 본인만 사용하는 앱입니다. 스마트폰에서 음악을 업로드하고 맥이 계산합니다. 공용 서버나 유료 AI API 키는 사용하지 않습니다.
- 앱을 벗어나도 맥의 작업이 이어지고, 다시 접속하면 진행 상태와 악보를 복구해야 합니다.
- GitHub는 소스 백업으로만 사용합니다. GitHub Pages, 저장소 공개 여부 또는 GitHub Actions에 앱 운영을 의존시키지 마세요.
- 변경 범위는 `richdisk/drum-score-studio`입니다. 다른 앱, 다른 앱의 배포 설정, 인증 정보는 수정하지 마세요.
- 정확도 검증 요청은 수정·재분석의 포괄적 허가가 아닙니다. 사용자가 검증만 요청하면 기존 음악·악보·설정을 보존하고 먼저 결과를 설명하세요.

## 구조와 핵심 파일

스마트폰 또는 맥 브라우저가 같은 origin의 FastAPI API로 음원을 전송합니다. 맥의 단일 작업 스레드가 분리와 채보를 처리하고 브라우저는 작업 ID로 결과를 받습니다. 원격 연결은 Tailscale Serve를 통한 소유자 전용 연결입니다.

| 파일 | 역할 |
| --- | --- |
| `index.html`, `styles.css` | 한국어 UI, 반응형 작업 화면 |
| `app.js` | 음원 재생, 악보 렌더링과 편집, MIDI/MusicXML/JSON 내보내기, 상태 복구 |
| `pro-client.js` | 동일 origin API, 업로드 ID 선저장, 재연결, 명시적 취소 |
| `workspace-store.js` | IndexedDB 음원·프로젝트 저장과 localStorage 복구 핸들 |
| `timing.js` | 검출된 박자 지도, 16분음표 격자, 중복 셀과 박자 오차 보고 |
| `engine/server.py` | 업로드·진행률·결과 API, 동시 작업 제한, 작업 메타데이터 보관 |
| `engine/pipeline.py` | 디코딩, Demucs 분리, ADTOF 채보, 피크 검출, BPM, 연주 MIDI |
| `engine/private_access.py` | loopback 및 Tailscale 소유자 확인 |
| `engine/requirements*.txt` | 고정한 실행·테스트 의존성 |
| `engine/tests/` | API, 보안, 타이밍, 내보내기, 재연결, 신호 처리 회귀 테스트 |
| `start.command`, `start-engine.py` | 전용 Python 환경 설치 및 로컬 실행 |

## 분석 모델과 제한

- Python 3.10–3.12, PyTorch 2.5.1, torchaudio 2.5.1입니다. 패키지 버전은 복구 시 임의로 최신으로 올리지 마세요.
- 분리 모델은 Demucs `htdemucs_ft`의 드럼 전문 구성원 `f7e0c4bc`입니다. 24초 단위에 양쪽 2초 문맥을 붙이고, 내부 6초 분할·50% 겹침으로 처리합니다.
- 채보는 ADTOF PyTorch 포트의 고정 커밋을 사용합니다. 100fps, 20초 단위에 양쪽 2초 문맥을 사용합니다. 누락·불일치 가중치로 무작위 추론하지 않도록 검사를 넣었습니다.
- 자동 분류는 킥·스네어·하이햇·탐·심벌 5종입니다. 탐 높이, 오픈/클로즈 하이햇, 라이드/크래시는 수동 확인해야 합니다. UI에 세부 악기가 있어도 모델이 모두 직접 구분한다는 뜻은 아닙니다.
- 현재 장치 선택 코드는 CUDA 또는 CPU입니다. Apple Silicon MPS 가속은 구현하지 않았습니다. 맥 CPU에서는 4분 곡도 수십 분 이상 걸릴 수 있습니다.
- 최대 12분·220MB이며 한 번에 한 곡을 처리합니다. 취소는 현재 오디오 구간 처리 후 반영됩니다.
- 악보 격자는 16분음표입니다. 셋잇단음표, 스윙, 빠른 연타와 변동 템포를 완전한 악보로 표현하지는 못합니다. 원래 타격 시점은 별도 연주 MIDI에 보존합니다.
- 모델 점수는 보정된 정확도 확률이 아닙니다. Velocity도 분리된 전체 드럼 에너지 기반 근사치입니다.
- Demucs와 ADTOF의 이용 조건은 README를 확인하세요. 특히 ADTOF의 비상업 이용 조건을 상업화 전에 검토해야 합니다.

## 창 복구 수정 내용

이전 버전은 작업 ID와 음원을 메모리에만 보관했고 시작 시 저장된 프로젝트를 복원하지 않았습니다. 네트워크 오류와 오래 열린 탭의 시간 제한도 분석을 끊는 원인이 될 수 있었습니다.

현재 버전은 업로드 전에 클라이언트 작업 ID를 저장하고, 서버가 같은 ID의 재전송을 중복 실행하지 않도록 합니다. 통신이 끊기면 같은 작업을 다시 확인하며, 탭이 숨겨지거나 오래 열려 있다는 이유로 작업을 자동 취소하지 않습니다. `visibilitychange`와 `pagehide`, 편집 시점에 저장합니다.

음원과 드럼 WAV는 IndexedDB에, 복구 핸들은 localStorage에 저장합니다. 같은 브라우저에서 새로고침하거나 창을 다시 열면 진행 작업, 완성 악보, 편집 상태를 복구합니다. 다른 기기에서는 서버의 최근 작업을 조회할 수 있지만 원곡·수동 편집의 기기 간 동기화는 구현하지 않았습니다.

완료 결과와 `job.json`은 엔진 재시작 후 복원합니다. 계산 중 엔진이나 맥이 종료되면 추론 자체를 중간 지점부터 이어가는 기능은 없습니다. 기존 코드가 캐시에 남는 문제를 막기 위해 정적 응답을 재검증하고 JS URL에 버전을 붙였습니다.

브라우저 저장 공간 제한, 시크릿 모드, 사이트 데이터 삭제에는 복구가 제한됩니다. 업로드가 끝나기 전에 모바일 브라우저가 강제 종료되면 전송 완료를 보장할 수 없습니다. 브라우저 간 동시 편집 충돌 해결 및 캐시 보관량 관리도 별도 개선 후보입니다.

## 정확도 검증의 현재 상태

사용자가 최근 완료 곡의 정확도가 아쉽다며 검증을 요청했습니다. 2026-09-09에 확인한 결과는 길이 약 253초, 민감도 85, 추정 BPM 125.28, 검출 타격 2,139개였습니다. 이 숫자는 당시 결과의 요약일 뿐 정답 대비 정확도나 오검출률이 아닙니다.

그 이후 사용자가 정답 악보가 개발에 도움이 되는지 물었고, 같은 음원 버전의 MIDI/MusicXML 또는 PDF·사진 악보를 요청했습니다. **정답 악보는 아직 전달받지 못했고, 해당 곡의 precision/recall/F1이나 악기별 오분류율은 산출하지 않았습니다.** 민감도 85가 오류의 원인이라는 결론도 아직 검증되지 않았습니다.

다음 검증은 같은 녹음의 정답인지 확인하고 시간축·반복 구간·드럼 기호를 맞추는 일부터 시작하세요. 원시 검출, 박자 검출, 악보 격자화, 드럼 세부 분류의 한계를 분리해 평가해야 합니다. 종이 악보가 단순화된 편곡이면 모든 차이를 오류로 집계하지 마세요. 민감도 변경 전후를 동일 음원·동일 정답·명시한 시간 허용 오차로 비교하고, 한 곡에만 맞춘 튜닝은 피하세요.

## 검증 기록

2026-10-05 소스 백업 전에 다음을 다시 실행했습니다.

| 검사 | 결과 |
| --- | --- |
| Node 회귀 테스트 | 14개 통과 |
| FastAPI 서버 테스트 | 9개 통과 |
| 개인 연결 접근 제어 테스트 | 2개 통과 |

총 30개 통과·1개 생략입니다. 잘못된 오디오를 모의한 테스트의 `ValueError` traceback은 의도된 출력이며 테스트는 통과했습니다. 이번 백업에서는 실제 곡을 새로 분석하거나 모델 정확도 벤치마크를 실행하지 않았습니다.

2026-09-09에는 독립 테스트 서버에서 분석 중 새로고침·창 닫기와 다시 열기·수동 음표 편집·드럼 재생 소스 복원을 확인했습니다. 실제 개인 주소에서도 같은 작업 ID로 복구되는 것을 확인했습니다. 이 검증을 스마트폰 모든 기종의 백그라운드 동작 또는 전문가 수준 채보 정확도 검증으로 확대 해석하지 마세요.

실행 명령은 README의 검증 절을 참조하세요. `engine/tests/resume_fixture.py`는 loopback 8767의 임시 작업 폴더에서 동작하는 **UI 복구 시험용 모의 분석기**입니다. 실제 AI 모델 또는 정답 악보를 대체하지 않습니다.

## 실행과 데이터 보존

새 환경에서는 `start.command` 또는 `python3.12 start-engine.py`를 실행합니다. 최초 설치에 인터넷·Python·Git이 필요합니다. UI와 API는 모두 `http://127.0.0.1:8765`에서 제공합니다.

이 맥은 저장소 밖의 `~/Library/Application Support/DrumScoreStudio` 복사본을 LaunchAgent로 실행합니다. 저장소 코드만 고쳐도 설치된 앱이 자동 업데이트되지는 않습니다. 정확한 머신별 경로·개인 URL·로그 위치는 로컬 인수인계 문서에 있으며 공개 저장소에는 개인 연결 설정을 넣지 않았습니다.

개인 연결 설정이 필요하면 `engine/private-access.example.json`을 참고해 `engine/.private-access.json`을 직접 만들고 실제 소유자와 주소를 입력하세요. 예시를 그대로 운영 설정으로 사용하지 마세요. 서버는 `127.0.0.1` 및 `--no-proxy-headers`를 유지해야 합니다. Funnel, 공용 바인딩, 와일드카드 CORS로 접근 제어를 약화하지 마세요.

서버의 입력 사본은 작업 종료 후 삭제합니다. 성공 결과는 24시간 경과 후 다음 업로드 때 정리합니다. 과거 결과가 필요하면 **새 업로드 전에** 별도로 보관하세요. 브라우저 저장 데이터는 GitHub 백업에 포함되지 않습니다.

1. 이 문서와 README, 새 채팅 요청문을 읽고 현재 Git 브랜치·작업 파일·실행 중인 작업을 다시 확인합니다.
2. 같은 맥이면 로컬 인수인계에 적힌 설치 복사본과 소스를 비교합니다. 실행 중인 분석이 있으면 허락 없이 재시작하지 않습니다.
3. 정확도 작업을 이어갈 때는 원곡, 생성된 JSON/MIDI, 같은 버전의 정답 악보를 먼저 확보합니다. 자료가 없으면 정확도 수치를 꾸며내지 않습니다.
4. 오류를 재현하고 검증 결과를 설명한 뒤, 사용자 요청 범위에 맞춰 수정합니다. 기존 프로젝트와 정답 파일을 덮어쓰지 않습니다.
5. 수정 후 회귀 테스트와 실제 브라우저 흐름을 검증합니다. 실행 복사본 반영은 작업이 없을 때 수행하고, GitHub에는 `drum-score-studio` 변경만 백업합니다.
